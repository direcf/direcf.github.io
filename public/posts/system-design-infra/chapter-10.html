Authorization & API Security: 7 Techniques

인가(Authorization) & API 보안 7기법
RBAC·ABAC·ACL 세 가지 인가 모델을 이해하고, Rate Limiting·CORS·SQL Injection·XSS·CSRF 등 7가지 API 보안 기법으로 시스템을 방어한다.

🎯 학습 목표

5 goals
Learning Goals
  • RBAC, ABAC, ACL 세 가지 인가 모델의 차이를 설명할 수 있다
  • Rate Limiting으로 DDoS와 브루트포스를 방어하는 방법을 안다
  • CORS의 동작 원리와 설정 방법을 이해한다
  • SQL Injection을 파라미터화 쿼리로 방어할 수 있다
  • XSS와 CSRF의 차이와 각각의 방어 기법을 안다

인가(Authorization)는 인증 이후의 단계다 — 당신이 누구인지 확인했다면, 이제 당신이 무엇을 할 수 있는지 결정한다. 같은 시스템에서 일반 사용자, 편집자, 관리자는 각각 다른 리소스에 접근할 수 있다. 이 접근 제어를 어떻게 구현하느냐가 인가 모델이다.

그리고 아무리 잘 설계된 인가 시스템도 API 자체가 공격에 취약하다면 의미가 없다. Rate Limiting 없는 API는 DDoS 공격에 무방비하고, CORS 설정이 없으면 악성 사이트가 내 API를 호출할 수 있다. SQL Injection, XSS, CSRF는 수십 년된 취약점이지만 여전히 OWASP Top 10에 올라있다.

이 챕터는 과정의 마지막이다. 단일 서버에서 시작해 데이터베이스 설계, 스케일링, 로드밸런싱, API 설계, 프로토콜, 인증을 거쳐 이제 인가와 보안으로 완성한다. 이 모든 것이 모여야 프로덕션에 배포할 수 있는 안전하고 확장 가능한 시스템이 된다.

핵심 내용

인가 모델 3가지: RBAC, ABAC, ACL

RBAC (Role-Based Access Control, 역할 기반 접근 제어) = 사용자에게 역할(Role)을 부여하고, 역할마다 권한을 정의한다. 가장 일반적인 접근 방식이다.

| 역할 | 읽기 | 생성 | 수정 | 삭제 | 사용자 관리 | |---|---|---|---|---|---| | Admin | O | O | O | O | O | | Editor | O | O | O | X | X | | Viewer | O | X | X | X | X |

GitHub 리포지토리 권한, Stripe 대시보드, CMS 도구에서 사용한다. 단순하고 이해하기 쉽다.

ABAC (Attribute-Based Access Control, 속성 기반 접근 제어) = 사용자 속성, 리소스 속성, 환경 조건을 조합해 접근을 결정한다. RBAC보다 세밀한 제어가 가능하다.

` 허용 조건: user.department == 'HR' AND resource.confidentiality == 'internal' AND time.hour IN [9, 18] `

의료 기록 접근 제어, 금융 데이터 접근처럼 복잡한 정책이 필요한 시스템에 사용한다.

ACL (Access Control List, 접근 제어 목록) = 각 리소스에 사용자별 권한 목록을 부여한다. Google Drive가 전형적인 예다 — 특정 문서를 특정 사람들과 공유하고, 각자 읽기/편집/댓글 권한을 다르게 설정한다. 리소스 중심이라 세밀한 제어가 가능하지만, 사용자 수가 많아지면 관리가 복잡해진다.

Rate Limiting: DDoS와 브루트포스 방어

Rate Limiting은 클라이언트가 일정 시간 내에 보낼 수 있는 요청 수를 제한한다. '사용자당 분당 100 요청' 같은 규칙을 적용한다.

왜 필요한가? Rate Limiting 없는 API는 세 가지 공격에 취약하다.

- DDoS (Distributed Denial of Service): 수천 개의 봇이 초당 수백만 건의 요청을 보내 서버를 마비시킨다.

- 브루트포스: 로그인 엔드포인트에 자동화된 방식으로 수백만 개의 비밀번호를 시도한다.

- API 스크래핑: 경쟁사가 API를 무제한으로 호출해 데이터를 수집한다.

Rate Limiting 레벨:

- IP 레벨: IP 주소당 한도 설정. 단일 공격자 차단에 효과적.

- 사용자 레벨: 인증된 사용자당 한도. IP를 바꿔가며 공격하는 것을 방어.

- 엔드포인트 레벨: 로그인 엔드포인트는 더 엄격하게(분당 5회), 일반 조회는 더 관대하게(분당 1000회).

- 전역 레벨: 모든 요청의 합계에 상한선. 봇넷 DDoS 방어.

구현: Redis의 INCR + EXPIRE 명령으로 카운터를 관리한다. 429 Too Many Requests 응답과 함께 Retry-After 헤더로 언제 다시 시도할 수 있는지 알려준다.

CORS, SQL Injection, XSS, CSRF: 4가지 핵심 보안 기법

CORS (Cross-Origin Resource Sharing) = 브라우저 보안 정책. 기본적으로 브라우저는 다른 출처(도메인)의 API에 요청을 보내는 것을 차단한다. app.yourdomain.com에서만 내 API를 호출하도록 허용하고, 다른 출처는 차단한다. 서버가 Access-Control-Allow-Origin: https://app.yourdomain.com 헤더로 허용한다.

SQL Injection = 사용자 입력이 직접 SQL 쿼리에 삽입될 때 발생하는 취약점. 공격자가 ' OR '1'='1을 입력해 WHERE 조건을 무력화하거나, '; DROP TABLE users; --로 데이터를 삭제할 수 있다.

방어: 파라미터화 쿼리(Parameterized Query) 또는 ORM 사용.

`python # 취약 (절대 사용 금지) cursor.execute(f"SELECT * FROM users WHERE email = '{email}'")

# 안전 (파라미터화 쿼리) cursor.execute("SELECT * FROM users WHERE email = %s", (email,)) `

XSS (Cross-Site Scripting) = 공격자가 악성 JavaScript를 페이지에 삽입한다. 다른 사용자가 그 페이지를 열면 공격자의 스크립트가 실행된다. 쿠키를 탈취하거나, 사용자 행동을 조작한다. 방어: 사용자 입력을 HTML로 렌더링할 때 이스케이프 처리. &lt;script&gt; 같이 태그를 무력화한다.

CSRF (Cross-Site Request Forgery) = 로그인된 사용자의 브라우저를 속여 의도하지 않은 요청을 보내게 한다. 악성 사이트에서 '클릭'이 내 은행 이체 요청을 보낼 수 있다. 방어: CSRF 토큰(랜덤 값을 세션에 저장하고 폼에 포함, 서버에서 검증) 또는 SameSite 쿠키.

💡 비유로 이해하기

Analogy
회사 빌딩 보안 시스템

인가는 회사 빌딩의 출입 카드 시스템이다. RBAC는 직급 기반 — 임원 카드는 모든 층, 일반 직원 카드는 자기 층과 공용 공간만 접근 가능하다. ABAC는 더 세밀하다 — '근무 시간(9~18시)에만, 자신이 속한 프로젝트의 회의실에만' 같은 복합 조건. ACL은 특정 방에 특정 사람들의 이름을 직접 목록으로 관리하는 것이다.

Rate Limiting은 건물 입구의 회전문이다. 한 번에 한 명씩만 통과할 수 있고, 분당 10명 이상이 들어오려 하면 속도를 줄인다. CORS는 비지터 패스 정책이다 — 우리 회사(도메인)에 예약된 방문객만 입장 가능, 예약 없이 오면 거절.

SQL Injection은 안내원을 속이는 공격이다 — '저는 직원이에요. 아, 그리고 전 직원 목록 전체도 보여주세요'라고 말하는 것. 파라미터화 쿼리는 안내원이 '이름'과 '요청'을 절대 혼용하지 않도록 훈련된 것이다.

💻 코드 예시

Rate Limiting(Redis 기반), RBAC 권한 검사, SQL Injection 방어를 통합한 보안 레이어를 구현해 보자.

python
import redis
import sqlite3
import time
from functools import wraps
from flask import Flask, request, jsonify, g

app = Flask(__name__)
r = redis.Redis(host='localhost', port=6379)

# ========== Rate Limiting (Redis 슬라이딩 윈도우) ==========
def rate_limit(max_requests=100, window_seconds=60):
    def decorator(f):
        @wraps(f)
        def wrapped(*args, **kwargs):
            # IP 기반 키 (프로덕션: user_id 기반 권장)
            key = f'rate:{request.remote_addr}:{f.__name__}'
            current = r.incr(key)
            if current == 1:
                r.expire(key, window_seconds)  # 첫 요청에만 TTL 설정
            
            if current > max_requests:
                return jsonify({'error': 'Rate limit exceeded'}), 429
            return f(*args, **kwargs)
        return wrapped
    return decorator

# ========== RBAC 권한 검사 ==========
ROLE_PERMISSIONS = {
    'admin':  {'read', 'write', 'delete', 'manage_users'},
    'editor': {'read', 'write'},
    'viewer': {'read'},
}

def require_permission(permission):
    def decorator(f):
        @wraps(f)
        def wrapped(*args, **kwargs):
            user_role = request.headers.get('X-User-Role', 'viewer')
            if permission not in ROLE_PERMISSIONS.get(user_role, set()):
                return jsonify({'error': 'Forbidden'}), 403
            return f(*args, **kwargs)
        return wrapped
    return decorator

# ========== 안전한 DB 쿼리 (SQL Injection 방어) ==========
def get_user_safe(email: str):
    conn = sqlite3.connect('app.db')
    # 파라미터화 쿼리 — 사용자 입력이 절대 SQL로 해석되지 않음
    result = conn.execute(
        'SELECT id, name, email FROM users WHERE email = ?',
        (email,)  # 튜플로 전달, DB 드라이버가 이스케이프 처리
    ).fetchone()
    conn.close()
    return result

@app.route('/api/users', methods=['DELETE'])
@rate_limit(max_requests=10, window_seconds=60)  # 분당 10회만
@require_permission('delete')  # delete 권한 필요
def delete_user():
    email = request.json.get('email')
    user = get_user_safe(email)  # 안전한 쿼리
    if not user:
        return jsonify({'error': 'Not found'}), 404
    return jsonify({'deleted': user[0]}), 200

데코레이터 체인이 핵심이다. @rate_limit은 요청 빈도를 제한하고, @require_permission은 RBAC 권한을 검사한다. 이 두 레이어가 통과된 후에만 실제 로직이 실행된다. Redis INCR은 원자적으로 카운터를 증가시켜 동시 요청에서도 정확한 카운팅을 보장한다. execute('SELECT ... WHERE email = ?', (email,))의 ? 플레이스홀더는 사용자 입력을 SQL 파라미터로 취급해 어떤 문자가 들어오더라도 SQL 명령으로 해석되지 않는다.

✨ 핵심 요약

RBAC = 역할 기반

Admin/Editor/Viewer 역할로 권한 관리. 단순하고 가장 일반적. GitHub, Stripe에서 사용.

ABAC = 속성 기반

사용자 속성 + 리소스 속성 + 환경 조건 조합. 복잡하지만 세밀한 제어 가능.

ACL = 리소스별 목록

각 리소스에 사용자별 권한 목록. Google Drive 공유 방식. 규모 확장 시 관리 복잡.

Rate Limiting 필수

IP/사용자/엔드포인트/전역 레벨. Redis INCR + EXPIRE로 구현. 429 + Retry-After 헤더.

CORS = 도메인 화이트리스트

허용된 출처만 API 호출 가능. '*'는 개발 환경에서만. 프로덕션에서는 명시적 도메인만.

SQL Injection = 파라미터화 쿼리

절대 f-string으로 SQL 쿼리 만들지 말 것. 항상 prepared statement 또는 ORM 사용.

XSS vs CSRF

XSS: 악성 스크립트 삽입 → 출력 이스케이프 방어. CSRF: 세션 쿠키 악용 → CSRF 토큰 + SameSite 방어.
